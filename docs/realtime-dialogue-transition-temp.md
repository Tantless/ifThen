# 临时说明：从推演改成实时对话

用途：用简单语言说明这次如何把原来的“单链推演 + 多链推演”改成“实时对话”。

## 一句话

以前是：用户改写一句后，系统替“我”和“对方”继续写一整段。

现在是：用户改写一句后，系统创建一个新的聊天分支。用户继续自己写“我”的消息，大模型只写“对方”的下一句。

## 旧方式的问题

原来有两种主要推演方式：

- 单链推演：用户改写一句，系统给出对方第一句反应。
- 多链推演：系统继续自动写几轮，“我”和“对方”都由模型代写。

这样做有几个不真实的地方：

- 模型代写“我”，容易不像真实用户本人。
- 系统一次性生成一段结果，用户不能像聊天一样中途补充。
- 用户如果又发了一句，新话很难自然合进已经生成的旧推演。

## 新方式怎么走

现在的流程变成这样：

1. 用户改写历史里自己发过的一句话。
2. 系统从这句话开始创建一个新的聊天分支。
3. 原聊天只显示到被改写的那一句，后面的原时间线先不展示。
4. 用户在新分支里继续发自己的消息。
5. 大模型只扮演“对方”，只回复对方下一句。
6. 对方回复回来后，前端把它拆成几条短气泡，按短句到长句逐条显示。

这样一来，用户仍然控制“我”怎么说，系统只负责模拟“对方”怎么回。

## 关键处理

### 1. 等用户说完再回

真实聊天里，用户常常会连续发两三句。前端不会每收到一句就立刻让模型回复，而是等大约 1.8 秒。

如果这段时间没有新消息，系统才请求对方回复。

### 2. 用户补话时丢掉旧回复

如果模型正在生成回复，但回复还没写入，用户又补发了一句，系统会把旧回复任务标记为过期。

旧结果即使后来返回，也不会写进当前聊天。系统会把用户最新的多条消息合在一起，再重新生成对方回复。

### 3. 模型只写“对方”

旧多链推演里，模型会同时写“我”和“对方”。

现在后端明确限制：模型只能生成“对方”的消息。“我”的消息只能来自用户输入。

### 4. 后端保存分支状态

后端新增了三类保存对象：

- 分支会话：记录这次改写从哪条消息开始、改写内容是什么、当前分支进行到哪里。
- 分支消息：记录新分支里每一条“我”和“对方”的消息。
- 回复任务：记录某一轮对方回复是否在排队、生成、完成、失败或已过期。

这些信息让系统知道：当前要回复的是哪几句话，旧回复还能不能用，以及最新聊天状态是什么。

## 前端改了什么

- 改写提交后，主体验不再进入旧推演结果页，而是进入新的分支聊天。
- 用户继续发消息时，消息会先显示在界面上，再保存到后端。
- 用户连续发消息时，前端会等待短暂空档，再触发对方回复。
- 对方正在回复时，界面会显示等待或输入中的状态。
- 对方回复失败时，界面会显示错误，并允许重试。
- 对方的一段回复会拆成几条短气泡，按节奏逐条出现。

旧的单链推演和多链推演还保留着，主要用于兼容和回归检查，但不再是改写后的主体验。

## 后端改了什么

- 新增了分支会话、分支消息、回复任务的保存结构。
- 新增了创建分支、读取分支、追加用户消息、创建回复任务、查询回复任务的接口。
- 后台处理回复任务时，会读取最新分支聊天内容，再让模型写“对方”的下一句。
- 写入回复前，后端会再次检查这轮任务是否已经过期。
- 如果用户已经补发了新消息，旧回复不会写入。
- 删除会话或重跑分析时，会一起清理相关分支数据。

## 改完后的效果

- “我”的话由用户自己写，更像本人。
- “对方”的话由模型生成，职责更单纯。
- 用户可以连续发消息、补充、打断，更像真实聊天。
- 系统不会把过期的旧回答硬塞进新对话。
- 原来的推演能力仍保留，但改写后的主要体验已经切到实时分支聊天。
